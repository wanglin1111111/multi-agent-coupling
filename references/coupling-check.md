# 耦合体检：拆不拆由任务耦合度决定

## 反直觉证据（为什么没有统一答案）

同一篇论文里的两个基准，方向相反：

| 基准 | 任务特征 | 多智能体 vs 单 Agent |
|---|---|---|
| 财务分析 | 信息流可分开收集、分别核对再合并 | **高 57%–80.8%**（四类多智能体架构） |
| PlanCraft 规划 | 顺序约束，后一步强依赖前一步状态 | **低 39%–70%** |

结论：不存在"多 Agent 更强"的统一答案。**原因变量是耦合方式，不是任务难度**——把顺序强依赖的任务硬拆成角色，消息传递和状态对齐会吃掉全部分工收益。

## 三问体检（每个候选子任务逐一问）

| # | 问题 | 不过的含义 |
|---|---|---|
| 1 | 能不能不看别人的中间状态就开工？ | 顺序强依赖；拆了之后每一步都在等上游，交接延迟叠加 |
| 2 | 交出来的是不是一个可独立验收的产物？ | 无法独立验收 = 拆了也看不见好坏，只能靠"信" |
| 3 | 中途会不会改到别人正在用的状态？ | 共享实时状态在交接中被稀释（见下） |

判定：**三问全过 → 并行候选；任一不过 → 留在同一个 Agent 循环**，用工具、Skills 和记忆解决。

## 工作能拆 ≠ 会话适合拆

判断标准不是"能不能分"，而是"每块能否**独立产出、独立验收**"。

实证参照：Anthropic 的电商场景用一个**持续运行的 Agent 循环 + Skills**，而不是拆多个 Agent——因为购物车、订单、用户偏好这类共享实时状态在多 Agent 交接中会被稀释，同时推高 token 和时延。单循环里这些状态天然在同一个上下文里，零交接成本。

## 拆分的正例/反例

| 场景 | 判定 | 理由 |
|---|---|---|
| 多数据源收集+分别核对+合并报告 | 拆 | 信息流可分、各自可验收（财务基准 +57% 的场景） |
| 长链规划（每步依赖上步状态） | 不拆 | 顺序强依赖（PlanCraft -39%~70% 的场景） |
| 改共享服务的代码（多人同时改状态） | 不拆或严格分区 | 中途互相改状态，冲突审查成本爆炸 |
| 独立模块的并行开发+独立测试 | 拆 | 三问全过 |
| 调研+写作（写作依赖调研中间态） | 不拆，或契约化交接 | 若写作只需要调研的**结论产物**→可拆；需要全部中间推理→不拆 |
