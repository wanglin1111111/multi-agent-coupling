# 基线与复测：四个数字决定留不留

## 第 2 步：建基线任务集（别先画架构图）

挑 **10–20 个**真实会遇到的代表性任务，固定三样：

1. **输入**：每次跑完全一致（文件/参数/环境）
2. **预期产物**：写清交付什么
3. **判定方法**：怎么算成功（测试/人工核对口径/评分标准）

让**单 Agent 先跑一遍**，记录四个数：

| 指标 | 记录什么 |
|---|---|
| 成功率 | 多少任务达到判定标准 |
| 耗时 | 每任务墙钟时间 |
| 调用量 | token / API 调用次数 |
| 典型错误 | 失败任务的错误模式（复测后对比"新增了什么错误"） |

**没有这条基线，后面任何"多 Agent 更快"都是自我感觉。**

## 第 7 步：同任务复测，只比四件事

同一批任务上再跑一次多 Agent 版，对比：

| 维度 | 判读 |
|---|---|
| 最终质量 | 用基线同一套判定方法，不许换口径 |
| 完成时间 | 墙钟时间（含交接等待） |
| 资源消耗 | token/调用量（多 Agent 通常翻倍，要算总账） |
| 新增的交接错误 | 基线没有、多 Agent 才出现的错误（状态丢失/上下文稀释/契约缺字段） |

裁决规则：**增益盖不住交接与纠错成本 → 退回单 Agent，回查拆法与验收**。删角色不是失败，是省成本。

## 数字边界（别拿论文数字当开关）

- 两个基准的百分比（+57%~80.8% / -39%~70%）**不能互比**（任务不同），也**不能直接预报业务收益**（你的任务耦合度可能两者都不像）
- 论文提到的约 **45% 单 Agent 基线分界是拟合出来的现象，不是可照搬的阈值规则**——"单 Agent 成功率低于 45% 就该上多 Agent"这种用法是误读
- 唯一合法的用法：**自己的任务、自己的基线、自己的复测差值**

## 复测记录的最低格式

```markdown
# 复测: <任务集名> @ <日期>
基线(单Agent): 成功率 X/20 | 平均耗时 Ys | 调用量 Z
多Agent版:    成功率 X'/20 | 平均耗时 Y's | 调用量 Z'
新增交接错误: N 件（模式: ...）
裁决: 保留 / 退回单Agent | 理由: 增益是否盖住交接+纠错成本
```
