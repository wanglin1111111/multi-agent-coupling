# 多智能体拆分判定：耦合度决定赚赔

> 源材料：多智能体实证对照（财务分析基准 vs PlanCraft 规划基准）+ Anthropic 单 Agent+Skills 电商场景实践
> 本文为 `multi-agent-coupling` 技能的方法论底座；可执行工作流见 `../SKILL.md`。

## 一、奥卡姆剃刀：剃掉装饰后，主题只剩一句

剃掉「多 Agent 到底更强还是更弱」的站队之争，剃掉「规划者/执行者/审查者」的角色图美观，剃掉 57% 与 39% 这类互相打架的百分比——剩下的最小解释只有一条：

**多智能体不是性能问题，是任务耦合度问题——子任务能否各自独立产出可检查的结果，决定了协作是赚还是赔。**

而验证它的唯一硬判据，是在同一个任务上复测单 Agent 与多 Agent 的差值，不是架构图好不好看。

## 二、核心分点总结

### ①【反直觉数据】——加 Agent 可能更好，也可能更差

同一篇论文里，财务分析基准上四类多智能体架构比单 Agent 高出 57%–80.8%；顺序约束的 PlanCraft 规划基准上反而低了 39%–70%。方向相反，说明不存在「多 Agent 更强」的统一答案。

### ②【原因变量】——耦合方式，不是任务难度

财务信息流可以分开收集、分别核对再合并；规划类任务后一步强依赖前一步状态。把后者硬拆成角色，消息传递和状态对齐会吃掉全部分工收益。

### ③【关键区分】——工作能拆 ≠ 会话适合拆

判断标准不是「能不能分」，而是「每块能否独立产出、独立验收」。Anthropic 的电商场景用一个持续运行的 Agent 循环 + Skills，正是为了避免购物车、订单、偏好这类共享实时状态在交接中被稀释，同时推高 token 和时延。

### ④【数字边界】——别拿论文数字当开关

两个基准的百分比不能互比，也不能直接预报业务收益；论文提到的约 45% 单 Agent 基线分界是拟合出来的现象，不是可照搬的阈值规则。

### ⑤【最小实现】——外面只加一层编排

单 Agent 的 ReAct 是内循环，多智能体的最小改动是在外面加编排层：为每个工作者建独立上下文，写清问题、可用输入与工具、预期交付物、停止条件；能独立的并行，有依赖的按顺序交接。

### ⑥【交接契约】——交回来的不能只是一句「完成了」

研究类任务要交回结论、依据、未解决问题；代码类要交回改动、测试结果、已知失败。共享状态只能通过任务输入或持久化产物传递，不能假设一个工作者知道另一个的上下文。

### ⑦【验收环节】——编排者负责查重、查冲突、退回修订

需要纠错时，加的是真能指出证据或测试失败的审查角色，而不是多生成一份相似答案。不合格退回，合格才合成。

### ⑧【四步顺序】——基线 → 分界 → 最小角色 → 同任务复测

第一固定任务集与判定口径并让单 Agent 先跑；第二标出能独立出结果的部分与必须共享状态的部分；第三只加必要角色；第四比较最终质量、耗时、资源消耗和新增的交接错误，收益不稳定就回查拆法与验收。

## 三、未来现实行动指南：怎么落进你的工作流

### 1）先建一条「基线任务集」，别先画架构图

挑 10–20 个你真实会遇到的代表性任务，固定输入、预期产物和判定方法，让单 Agent 跑一遍，记录成功率、耗时、调用量、典型错误。没有这条基线，后面任何「多 Agent 更快」都是自我感觉。

### 2）做一张耦合体检表，三问定拆不拆

每个子任务问：① 能不能不看别人的中间状态就开工？② 交出来的是不是一个可独立验收的产物？③ 中途会不会改到别人正在用的状态？三问全过 → 并行候选；任一不过 → 留在同一个 Agent 循环里，用工具、Skills 和记忆解决，别拆。

### 3）把交接写成「契约模板」，而不是口头分工

每个子任务单里固定写：问题定义、可用输入与工具、交付物格式、停止条件、必须回传的字段（结论/依据/未解决项）。共享状态一律走任务输入或落盘产物，禁止靠上下文默契。

### 4）用四个数字做复测，决定留不留

同一批任务上再跑一次多 Agent，只比四件事：最终质量、完成时间、资源消耗、新增的交接错误。增益盖不住交接与纠错成本，就退回单 Agent——删角色不是失败，是省成本。

### 5）默认不拆，把「加 Agent」当成需要举证的动作

以后遇到「要不要搞个多智能体」的需求，先要求对方回答一句：多这一次协作，换回了什么可验证的收益？答不上来，就先加工具、加 Skills、加审查环节，这三项的边际收益通常比加角色高得多。
